### The caveat that is not a footnote

This ran under Docker Desktop on macOS, which is a Linux virtual machine with a
virtualised disk. **Its disk behaviour is not a VPS's.** `fsync` in that VM does not
mean what `fsync` on a cloud provider's network-attached block device means, and this
store commits per write — so the write numbers below are the ones most exposed to
that difference, and could move by an order of magnitude in either direction on real
hardware. That is the reason these numbers are a shape rather than a promise. Do not
quote the absolute rows/second at anybody.

Which comparisons survive that is not uniform, so it is worth saying once rather than
leaving a reader to guess. **The ratio between insert and delete holds**: they ran
minutes apart on the same profile against the same store. **The ratio between profiles
holds for scan and delete**, where all three profiles agree to within a few percent —
three independent runs landing on the same number is itself the evidence that the host
was not moving under them. **It does not hold for insert**; that section says why.

## What happens at the wall

One profile — **tiny** — was pushed until it stopped. The workload is the mistake an
application actually makes: a scan declared once, with a limit far above what the
collection held at the time, asked for again after the collection has grown. Each rung
adds rows and then asks for all of them at once.

| rows in the collection | about | seconds | what the server did |
|---|---|---|---|
| 5000 | 9.8 MiB | 0.1 | answered with 5000 rows |
| 10000 | 19.5 MiB | 0.2 | hung up mid-answer, and was still serving afterwards: EOF |
| 15000 | 29.3 MiB | 0.3 | hung up mid-answer, and was still serving afterwards: EOF |
| 20000 | 39.1 MiB | 0.4 | hung up mid-answer, and was still serving afterwards: EOF |
| 25000 | 48.8 MiB | 0.5 | hung up mid-answer, and was still serving afterwards: EOF |
| 30000 | 58.6 MiB | 0.7 | hung up mid-answer, and was still serving afterwards: EOF |
| 35000 | 68.4 MiB | 1.4 | hung up mid-answer, and was still serving afterwards: EOF |
| 40000 | 78.1 MiB | 1.0 | hung up mid-answer, and was still serving afterwards: EOF |
| 45000 | 87.9 MiB | 2.0 | **did not come back, and the server was gone**: EOF |

**Verdict: died_reading.** The server was gone when the phase ended.

at 45000 rows the read took the server with it: EOF | redial: dial tcp 172.20.0.2:7433: connect: connection refused | redial afterwards: dial tcp 172.20.0.2:7433: connect: connection refused

Peak sampled during the wall phase: 352.2 MiB over 31 samples — a lower bound, for the reason below.

What docker says about that container afterwards: status `exited`, exit code `137`, OOM-killed `true`, restarts `0`.

The restart count matters for reading the table above. A rung that says the server
hung up and was serving afterwards would be a lie if something had restarted the
process in between; `restart: "no"` in the compose file is why it cannot, and this
is the reading that says it did not.

## How to read the memory column

Peak memory is sampled from outside with `docker stats`, about once a second, for the
duration of that phase and nothing else. Two things follow, and both make it a lower
bound rather than a measurement of the true peak: a spike between two samples is not
seen at all, and the process's last moments before an out-of-memory kill are exactly
the moments most likely to fall between them. What `docker stats` reports is the
cgroup's current usage less its inactive file cache, so it is closer to what the
process is holding than to what the kernel has charged the cgroup — but it is not the
same number the OOM killer looks at.
